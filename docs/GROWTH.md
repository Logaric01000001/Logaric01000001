# Sustainable open-source growth

## Position

Logaric builds inspectable Linux tools and documents practical software/security learning. Lead with a useful artifact and its limits, rather than skill lists or unearned expertise.

## First 30 days

| Week | Deliverable | Evidence |
| --- | --- | --- |
| 1 | Bilingual entry points and Antena field note | Merged changes and working links after publication |
| 2 | One sanitized hardware observation or reproducible Antena bug | Environment, steps and actual result; no guessed success |
| 3 | One small upstream contribution in a tool actually used | Read contribution rules, reproduce a real issue, submit a focused fix |
| 4 | A concise technical article explaining the observed problem and fix | Link to code and limitations; answer substantive replies |

Two 45-minute sessions each week are enough to keep this cadence manageable. Prefer one completed, useful change over several promotional posts.

## Participation

Use project Issues for actionable reports and reproducible requests. Discussions, when enabled, should hold open questions and hardware experiences. Before posting to any Linux or security community, read its current rules and self-promotion policy. Share an explanation useful without clicking the project link. Do not mass-post, automate follows/stars, send unsolicited DMs or manufacture contribution activity.

Choose upstream tasks only after checking current contribution guidance and reproducing the problem. Do not open a generic “how can I help?” issue as a substitute for a contribution.

## Measurements

Baseline audit, 2026-10-29: public profile showed 5 followers; five public repositories were returned; repository metadata showed 0 stars for the audited repositories. These are observations, not targets or promised outcomes.

Record weekly: substantive reports, merged external contributions, repeat collaborators, and (when owner traffic access is available) unique visitors and clones. Counts should be observed manually or through first-party GitHub tools; no tracking pixel is added. A useful issue from a real user matters more than an isolated star.

## Public contact

Use repository Issues for project work. Do not publish personal contact data or turn Issues into a job-offer inbox. Decide on a dedicated professional contact address separately before publishing one.
